# ADR-0008：MCP 利用制限を1プロセスのメモリ内で管理する

## 状態

採用。Issue #27 の方針を記録した。実装・検証の結果は [作業記録](../worklogs/27-mcp-usage-limits.md) を参照する。

## 背景と比較

クライアントのモデルが分析しても、MCP サーバーの収集は通信・CPU・メモリを使う。1回の件数・ページ数・期限だけでは、繰り返しの収集と同時処理を制限できない。

- メモリ内の固定窓は依存を増やさず、時計を差し替えて境界と判定を検証できる。再起動と複数台の継続性、境界付近の集中を防ぐ保証は持たない。
- sliding window や token bucket は集中の平準化に適するが、今回の開始回数という契約より状態管理と説明が増える。
- DB や Redis による共有状態は再起動と複数台に対応できるが、永続化の運用・原子的な受付・障害時の拒否方針を別途決める必要がある。
- IP による分類はプロキシ・共有回線・転送ヘッダーの信頼に依存する。認証済み利用者がない現在の段階では、利用者の予算を保証できない。

## 決定

1つの MCP handler が全利用者で共有する固定窓と同時実行数を所有し、mutex 内で受付と更新を一体にする。HTTP ごとに MCP Server を作る既存方式でも、この状態だけは共有する。取得先・context は既存の境界のまま注入し、収集ユースケースと CLI に利用制限を混ぜない。

初期値は1分6回・24時間100回・同時2件とし、環境変数で変更する。入力検査・開始前キャンセルの確認を先に行い、拒否時は Steam に接続せず MCP のエラー結果を返す。受け付けた開始回数は失敗しても消費し、同時枠は結果変換を含む処理終了時に返却する。詳細は [利用制限仕様](../specs/mcp-usage-limits.md) に置く。

## 利点と制約

ローカルの1プロセスで通信と同時負荷の増加を抑え、実 SDK と時計差し替え・race で契約を検証できる。再起動時は回数が消え、複数台では台数分の枠となる。固定窓の境界では短時間の集中が起こる。認証、共有予算、拒否トラフィックへの対策、クラウドの請求上限は保証しない。

Render の [プラン](https://render.com/docs/platform-features-by-plan) と [帯域](https://render.com/docs/outbound-bandwidth) は別の料金条件を持ち、[Free の制約](https://render.com/docs/free) もある。Hobby を選んだだけで実行費用が常に無料になるとは扱わない。公開構成・配置先を決める際にその時点の公式条件を確認する。
