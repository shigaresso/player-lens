# MCP レビュー収集の利用制限

LimitsConfig・Limits・NewLimits・DefaultLimits と Limiter は reviewmcp/domain に置く。MCP adapter が状態を所有し、application が確保と defer による返却を担当する。 配置は [ADR-0013](../adr/0013-domain-folder-layers.md) に従う。

## 目的と適用範囲

[Issue #27](https://github.com/shigaresso/player-lens/issues/27) で、`/tools` の `collect_reviews` を繰り返し呼び出した場合の Steam 通信と実行資源を制限する。分析は接続元のモデルが担当するが、レビュー収集は PlayerLens が担当するため、その利用量は別に管理する。

1つの `reviewmcp.NewHandler` が状態を所有する。main はプロセスにつき1つだけ組み立て、HTTP リクエストごとの MCP Server、複数セッション、対応する4つのプロトコルで同じ枠を使う。IP・転送ヘッダー・利用者単位では数えない。CLI・healthz・初期処理・ツール一覧・未定義ツールには適用しない。

## 設定

| 環境変数 | 既定値 | 意味 |
| --- | --- | --- |
| `MCP_REQUESTS_PER_MINUTE` | 6 | 1分の窓で受け付ける収集開始回数 |
| `MCP_REQUESTS_PER_DAY` | 100 | 24時間の窓で受け付ける収集開始回数 |
| `MCP_MAX_CONCURRENT` | 2 | 完了していない収集処理の同時数 |

空なら既定値を使う。符号・空白なしの10進整数1〜2147483647を受け付け、先頭の0は数値へ正規化する。0・負数・小数・文字列・範囲外は、HTTP の待ち受け前に非0で起動を失敗させる。0による無制限化は提供しない。Compose と `.env.example` に同じ設定を記載する。本番は実行環境から渡し、秘密情報・`.env` をイメージへ入れない。

### 設定値の生成と検証（Issue #54）

`LimitsConfig` は公開フィールドを持つ未検証の設定値、`Limits` は非公開フィールドに設定値のコピーを保持する生成済みの値とする。`NewLimits` が各上限の正数検査を担当し、不正時はゼロ値と `steamdomain.ErrInvalidArgument` を保持するエラーを返す。分次・日次は独立した上限であり、日次が分次より小さくても受け付ける。Go API の正数条件は維持し、環境変数の31 bit 制約を生成 API へ一律に追加しない。

`ReadMCPLimits` は環境変数の文字列を解析して `LimitsConfig` を作り、`NewLimits` で生成する。`DefaultLimits` は分6回・24時間100回・同時2件の有効な値を返す。`Limits.Config()` が返すコピーや生成元の設定を変更しても、生成済みの値に影響しない。生成だけでは通信・時計の参照・利用枠の消費は行わない。

Issue #101 では、同じ cmd/server/adapter/limits.go の中で読み取りと解析を分ける。公開する ReadMCPLimits は、分次・24時間・同時数の環境変数をこの順で各1回読み、非公開の mcpLimitsInput に文字列を保持する。全項目を取得してから parseMCPLimits で既定値の適用・31 bit の数値変換を行い、成功した LimitsConfig を NewLimits へ渡す。解析関数は文字列の値だけを受け取り、環境変数や取得関数・通信などの I/O に依存しない。入力型・解析関数は別ファイルや新しいパッケージへ分けず、公開 API を増やさない。

数値の0は変換には成功し、NewLimits の正数条件で拒否する。複数の不正値がある場合も、分次・24時間・同時数の順に数値変換を行い、すべての変換に成功してから正数条件を検査する既存の順序を維持する。変換失敗では環境変数名・既存の説明と strconv の原因を保持し、解析関数はゼロ値の LimitsConfig を返す。ReadMCPLimits の失敗は引き続きゼロ値の Limits と原因を返す。読み取りと解析の分離により、途中の変換失敗時も先に3項目を読み終えるが、公開する設定値・起動失敗の契約は変更しない。

`NewHandler` は生成済みの値を受け取り、各上限を再検査しない。Go で作成できる `Limits{}` は未初期化のゼロ値であり、`NewHandler` が `steamdomain.ErrInvalidArgument` として拒否する。型だけでゼロ値の生成まで排除したとは扱わない。生成後の設定値と、handler が所有する利用回数・窓・同時実行数の状態は区別し、状態の寿命と共有範囲は維持する。

## 受付と固定窓

1. adapter が入力を検査し、MCP の既定値・上限を適用した CollectionOptionsConfig から NewCollectionOptions で有効な条件を生成する。不正入力は既存の `invalid_input` を返し、利用枠を消費しない。application は有効な CollectionOptions を受け取り、条件を再正規化しない（[ADR-0015](../adr/0015-collection-options-boundary.md)）。
2. context が開始前に終了している場合は、MCP 用 application が共通の NewFailedCollection で空の失敗結果を作り、respond を一度呼んで早期 return する。下位の収集・期限の生成・利用枠の確保を呼ばず、開始回数・同時枠・時計を消費しない。入力条件・空の非 nil レビュー配列・StopFailed と元のキャンセル／期限超過の原因を保持する。
3. mutex 内で時計を読み、日次・分次・同時数の順に判定する。上限に達していれば取得せず拒否する。
4. 全条件を満たした場合だけ、日次・分次の回数と同時数を増やす。取得・JSON 変換・応答量の判定を終えるまで同時枠を保有し、defer で返却する。

Issue #62 では application の CollectReviews が同期的な結果処理関数を呼び、その完了まで枠を保持する。adapter が渡す関数は JSON・失敗分類・応答量判定・SDK 応答生成を完了してから戻り、変換に失敗しても確保済みの枠は返却する。生成した応答の HTTP 送信完了までは範囲に含めない。結果処理は成功・取得失敗・拒否・開始前キャンセルで一度だけ呼び、処理のエラーを返す。拒否と開始前キャンセルでは確保していない枠を返さない。[ADR-0016](../adr/0016-mcp-response-slot-lifetime.md) に従う。

最初の有効な受付を窓の起点とし、1分と24時間の独立した固定窓を持つ。次の判定時刻が開始時刻+期間以上なら、その窓の回数を0へ戻して判定時刻から次の窓を始める。別の窓や処理中の同時枠をリセットしない。24時間は暦日の0時を意味しない。時計は差し替えて、期間の直前・ちょうど・直後を実時間待機なしで検証する。

受け付けた収集開始を1回として数える。1回内のページングは既存の最大5ページに従う。空の結果・成功・途中失敗・実行中のキャンセル・期限超過・応答量超過でも、開始回数は返却しない。拒否と入力不正、開始前のキャンセルでは回数を消費しない。同時枠は成功・失敗とも返し、二重の返却で枠を増やさない。 同じ goroutine の収集中・結果処理中に panic が発生した場合も defer で確保済みの枠を返す。panic はここで握りつぶさず呼び出し側へ伝播し、開始回数は戻さない。

## 拒否応答

limiter は非公開の usageRejectionReason で受付結果を返す。ゼロ値は拒否なし、残る定義値は日次・分次・同時数の上限到達を表し、公開コードを含めない。usageFailure が公開コードと説明文へ変換する。拒否なしはゼロ値の公開情報となる。未定義の内部値はプログラミングエラーとして panic し、外部入力からこの理由型を直接生成しない。

| 原因 | `error_code` | 回復条件 |
| --- | --- | --- |
| 24時間の上限 | `daily_limit_reached` | 日次の窓が更新された |
| 1分の上限 | `rate_limited` | 分次の窓が更新された |
| 同時数の上限 | `busy` | 受付済みの処理が終了した |

拒否時の Collection も steam/domain.NewFailedCollection で生成し、従来の入力条件・nil のレビュー配列・成功ページ数0と拒否理由を維持する。公開 JSON のレビュー配列は従来どおり空配列とする。

HTTP 200 の MCP `CallToolResult` に `isError=true` を返す。収集条件と App ID を保持し、レビュー配列は空、`returned_count=0`、`omitted_reviews=0`、`pages_fetched=0`、`stop_reason=failed` とする。構造化結果と JSON テキストの契約を維持する。待機・自動再試行・HTTP 429 は追加しない。モデルへの案内だけで無限再試行を防いだとは判断しない。

## 検証と保証の範囲

ユニットテストで時計の境界、拒否時の非消費、判定の優先順、並行受付、二重返却、失敗後の再受付を確認する。実 SDK クライアントとの結合テストで、別セッション・異なるプロトコル・初期処理・入力エラーから枠を回避できないことを確認する。race detector を併用し、通常テストと CI は実 Steam・実 LLM を呼ばない。本番イメージでも3つの不正設定を非0で拒否する。

状態はメモリ内であり、再起動で消える。複数の handler・プロセス・インスタンスを作ればそれぞれ枠を持つ。固定窓の境界前後には短時間に上限の2倍まで受付が集中し得る。任意の連続する1分・24時間に対する厳密な上限や、永続した利用予算ではない。

拒否応答・インフラ稼働にも資源と費用が必要なため、クラウドの請求額を保証する制限ではない。Issue #29 で、認証なしの公開 MCP に [許可 Host の検査](mcp-public-access.md) を追加した。複数プロセスの共有予算・配置先の使用量管理と、バックエンド分析の利用コード・利用期限は別 Issue で決定する。Render Hobby のワークスペース料金と、実行プラン・帯域の料金は区別する。

採用理由は [ADR-0008](../adr/0008-mcp-usage-limits.md)、実装と実行した検証は [作業記録](../worklogs/27-mcp-usage-limits.md) に残す。
