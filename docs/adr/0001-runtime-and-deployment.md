# ADR-0001：Go・Docker・Render による実行・配置

## 状態

採用。ユーザーが合意した実行・配置方針を記録した。Issue #11 で最小 HTTP サーバー、Compose、本番用イメージと検証 CI の設定を追加した。リリース対象の公開・配置経路と Render 配置は未導入であり、本番接続を保証する文書ではない。ローカル検証・実 CI の状態は [作業記録](../worklogs/11-http-server.md)、運用規約を検査する CI の導入状態は [ADR-0002](0002-conventions-tooling.md) で扱う。

## 背景

PlayerLens は、レビュー収集・分析・レポート生成の操作を Web、MCP、CLI、定期実行から利用する方針とする。ポートフォリオとして、開発環境を再現でき、検証した成果物を特定できる構成を求める。

## 比較した選択肢

| 選択肢 | 判断 |
| --- | --- |
| TypeScript を主な実装言語として使う | Go で開発するという今回の合意に従い、採用しない |
| ホスト上の Go で開発し、配置時に再ビルドする | 環境差と成果物の違いを管理する必要があるため、通常の開発・リリース経路には採用しない |
| Docker Compose で開発し、本番イメージを一度ビルド・検証して配置する | 再現可能な開発構成とリリース対象の特定のため採用する |
| Cloudflare を配置先にする | 比較後のユーザーの選択に従い、現時点の配置先には採用しない |
| Render の Hobby ワークスペースを使う | 現時点の配置先として採用する。各サービスの実行プランは別途決める |

現在の料金・各製品の優劣はこの記録では確定しない。契約やサービス構成を決定する Issue で、その時点の公式仕様・料金を確認する。

## 決定

- 主な実装言語は Go とする。Web・MCP などの入口から、同じ操作全体を担う処理を呼び出す。
- 通常の開発は Docker Compose を使い、ソース共有・再読み込みを利用する開発用構成と、本番用イメージを分ける。
- 本番用イメージはソース共有やホスト側の Go 実行に依存せずに検証する。リリース対象は一度ビルド・検証し、その同じイメージを digest で特定して Render へ配置する。
- PR 時の検証と、マージ後にビルドしたリリース対象の検証を区別する。
- Render のワークスペースは Hobby を選ぶ。サービス構成は `render.yaml` などで明示し、ローカルの Compose 構成と区別する。
- 永続化方式は、この決定に含めない。[データ・調査仕様](../specs/data-and-research.md) を満たす方式を別の Issue・ADR で決める。

### Issue #11 の初期構成

- Go 1.27.1 と `golang:1.27.1-bookworm`、`distroless/static-debian12:nonroot` のマルチアーキテクチャ index digest を Dockerfile に固定した。タグは版の説明、digest は取得内容の特定に使う。更新時は Go のパッチ版・go.mod・digest を同じ Issue で変更し、ローカルと CI と本番用イメージを再検証する。
- 開発用には Go のコンパイラを含め、Compose Watch でソースを同期して再起動する。`go run` の子プロセスへ終了シグナルを伝える問題を避けるため、ビルドしたバイナリを `exec` する。検証用のソース共有は読み取り専用とし、ビルド・モジュールのキャッシュだけを volume へ置く。
- Issue #25 で MCP SDK を導入し、go.mod・go.sum を管理する。Dockerfile は両方をコピーして依存を取得し、Watch はモジュール変更時に再ビルドする。cmd・internal の変更時は同期・再起動する。
- 本番用には実行ファイルと証明書を含む Distroless を使い、非 root で実行する。現在の MCP SDK を含む依存は CGO 不要なので本番ビルドで CGO を無効にする。CGO 依存を導入するときはビルドと実行用ライブラリを見直す。
- スモーク検査は一度ビルドした image ID を再利用する。これはローカルのイメージを特定するものであり、registry の manifest digest や配置対象の公開・検証を代用しない。ホストと CI のアーキテクチャは異なる場合があり、ローカル arm64 の成功だけで CI の amd64 を検証済みとは扱わない。

### Git 情報に依存しない Go 実行（Issue #23）

- Dockerfile の development ステージで `GOFLAGS=-buildvcs=false` を設定する。app・collect・verify・format と、development を継承する lint・本番ビルドへ共通に適用し、テストから起動する子 Go コマンドにも引き継ぐ。個々のコマンドへ同じフラグを重複して追加しない。
- Git の所有権・読み取り権限、Git コマンドや `.git` の有無を理由に Go のビルド・検証を失敗させない。環境変数を上書きする起動経路やホスト上の直接実行は、この共通設定の保証範囲へ含めない。
- バイナリへ VCS revision・時刻・変更状態を自動埋め込みする機能は使用しない。ソースの対象 SHA と成果物の対応は GitHub CI・作業記録、イメージ ID・digest で管理する。配置経路の導入状態は既存の記録に従う。
- `scripts/verify_go_vcs.sh` を integration の共通検査へ接続する。隔離した一時モジュールで Git が128を返す場合、Git が PATH にない場合、`.git` がない場合の `go list`・`go build`・`go test` とテスト内の子ビルドを実行する。失敗は検査全体へ伝播し、一時資源は終了時に削除する。ホストの Git 設定・safe.directory は変更しない。
- コミット・範囲・Issue・PR・Release の規約検査に必要な Git・GitHub 接続は維持する。取得できない場合に成功扱いへ変更しない。

### 開発用のホストポート選択

- Python 標準ライブラリの `scripts/dev.py` から Compose を起動する。既存の開発ツールに Python が必要なので、ホスト Go や追加のパッケージを要求しない。
- 事前のソケット検査は Docker の割り当てまでに競合する可能性があるため、実際の Docker のホストポート割り当て失敗を使って `DEV_PORT` を1ずつ増やす。Docker が出力する既知のポート使用中エラーだけを再試行し、他の失敗を隠さない。Docker のエラー表現が変わった場合は中断する。
- Compose の設定解決で `.env` とシェル環境変数を扱い、選択値だけを子プロセスへ渡す。本番の `PORT` と bind 失敗の契約は維持する。ランダムな公開ポートは、連番で選びたい要件に合わないため採用しない。
- ビルド後に `up --detach --wait --no-build` で起動と healthcheck を確認し、`watch --no-up` で再ビルド・起動を繰り返さずソースを監視する。終了時は起動入口が `app` を停止する。同じ Compose プロジェクトの同時起動と remote Docker のポート探索は扱わない。

## 配置時の条件

- アプリケーションは Render の `PORT` に対応し、外部から接続できるアドレスで待ち受ける。
- HTTP のヘルスチェックと終了時の処理を用意する。
- 秘密情報は実行環境から渡し、Git・Docker イメージに含めない。
- 配置後に実際の URL で Web と MCP の接続を確認する。同じイメージでも、設定、資源制限、通信、外部 API の違いを確認する。

## 利点と制約

- 開発環境を Compose の構成として共有できる。ただし、開発用構成と本番用イメージは用途が異なるため、両方を確認する必要がある。
- digest で成果物を特定できる。ただし、同じイメージであることだけでは、配置先の設定と動作の一致を保証しない。
- Docker の利用と永続化は別の設計事項となる。ローカルの Compose volume が Render に引き継がれるとは扱わない。
- Render のワークスペースプランとサービスの実行プランは別となる。Hobby の選択だけで常時稼働・永続ディスクが提供されるとは判断しない。
- イメージ検証用 CI の設定は Issue #11 で追加したが、実行結果は対象 SHA を確認して記録する。リリース対象の公開・配置用 CI、配置経路、サービス実行プランは今後導入・決定する。運用規約のフック・CI は [ADR-0002](0002-conventions-tooling.md) に従う。必要な費用・運用負担は各導入 Issue に記録する。
