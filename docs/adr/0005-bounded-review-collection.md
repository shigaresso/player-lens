# ADR-0005：上限と部分結果を持つ収集操作を導入する

## 状態と対象

採用。[Issue #21](https://github.com/shigaresso/player-lens/issues/21) の `steam.CollectReviews` に適用する。契約は [収集仕様](../specs/collect-reviews.md)、操作の境界は [ユースケース](../use-cases.md) を参照する。

配置の決定は [ADR-0013](0013-domain-folder-layers.md) で部分的に置き換えた。以下の収集・保存・失敗・資源の振る舞いは維持する。現在の配置は各領域内の domain・application・adapter とする。

## 背景と比較

1ページ取得 adapter だけでは件数・時間・ページ数の上限、重複や途中失敗を管理できない。Steam の公開 API は1ページ最大100件で、続きのカーソルを使って取得する。

| 選択肢 | 判断 |
| --- | --- |
| HTTP adapter の中にページングを追加する | 1回の通信と操作全体の終了条件・部分結果が混在するため採用しない |
| 各 CLI・Web・MCP の入口に収集手順を置く | 判断が重複するため採用しない |
| 有限の上限を持つ独立した収集操作にする | 小さな取得 interface を渡し、テストと入口で同じ操作を使うため採用する |
| 途中失敗で取得済みレビューをすべて捨てる | 成功範囲と未完了を区別できる部分結果を優先し、採用しない |

## 決定

- 現段階は Steam 固有の操作として同じ `steam` パッケージに置く。汎用のレビュー型・保存層・ジョブを先に増やさず、利用側の `PageFetcher` に `Client` を渡す。
- 既定は1000件・1ページ100件、上限は1万件・100ページ・2分とする。メモリと通信の無制限な走査を避けるアプリ独自の値とし、Steam の QPS の推測とは区別する。
- 1回の収集内は ID による最初の値の保持と取得順を採用する。本文の更新と永続的な版の判定は保存設計に委ねる。
- 空ページ、件数・ページ上限、失敗を終了理由で区別する。取得したページで循環を見つけた場合はそのページを含む部分結果を返す。入力不正ではゼロ値を返す。
- 429などで収集側の再試行は行わない。回数・待機・再開・保存の責務をまとめて決める後続 Issue で検討する。期限は context で伝播し、依存が尊重する契約を設ける。

## 利点と制約

正常系と失敗を制御した取得依存で検証でき、入口に調査手順を重複させない。実 API は一度の少量の手動確認に分け、通常テスト・CI は外部 Steam に依存しない。

件数・ページ上限での成功は全件取得ではない。更新中のページの同一時点の完全性や最新性、1万件を時間内に必ず集められることは保証しない。部分結果はプロセス内の値であり、保存・再開・本文版や分析との紐付けは別 Issue で実装する。
