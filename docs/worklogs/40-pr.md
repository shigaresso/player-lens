## 背景・目的

MCP の収集処理に実行手順と公開用エラーの選択、応答の組み立てが混在していた。入力・利用枠・期限・収集を行う手順を追いやすくするため、通信しない結果・エラー変換を分離した。本文省略後も大きい応答を有限に処理する終了条件も定めた。

## 変更内容

- 収集エラーから公開コード・説明文を選ぶ処理を failure.go に分離した。公開情報の型を toolFailureInfo とし、元の error の保持と役割を区別し、encodeResult・marshalToolResult まで情報型を一つの引数として渡した。
- limiter の受付結果を非公開の usageRejectionReason と定数で表し、usageFailure で MCP の公開コード・説明文へ変換した。日次・分次・同時数の判定順序、拒否時の非消費、枠の返却を維持した。
- ガイドを含む応答の組み立て、SDK の結果全体の128 KiB検査、本文省略と原因保持を result.go に分離した。
- 通常応答と省略応答のサイズ判定を encodeResult に集約し、本文省略を一度に限定した。省略件数を内部で決め、省略後も超過する場合は変換エラーで終了させた。応答生成失敗でも収集・変換の両原因を保持し、表示文言から内部原因を除いた。
- collection.go に入力解析、利用枠と context の管理、収集操作の呼び出しを残した。枠の返却タイミングと入出力 schema・コード・メッセージを維持した。
- 複合原因の優先順位、部分失敗と応答量超過の組み合わせ、拒否理由から公開情報への変換をテストし、仕様・ADR-0008・ユースケースと作業記録を更新した。

## 検証

既存動作の回帰テストは一つずつ Green を確認して先にコミットし、実装整理後も Green を確認した。型名の改名と公開情報の引数整理では、既存テストの期待結果を維持し、形式上の Red を作らなかった。拒否理由の分離では変換の契約と型参照を先にテストへ記述し、未実装の理由型・定数による Red、実装後の同じ関連テストの Green を確認した。正常な受付、3種類の拒否、内部の未定義値の扱いを検証した。

省略後も大きいメタデータの終了条件は、2引数の入口 API の未実装による Red と有限な処理の実装後の Green を確認した。旧再帰処理を大きな入力で実行していない。続いて、応答生成失敗と収集失敗の複合時に収集原因を失う Red を確認し、原因保持と安全な表示文言を実装して Green を確認した。
