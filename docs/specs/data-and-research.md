# データ・調査仕様

## 目的と状態

プレイヤーのレビューを収集・分析し、ゲーム企画に使える根拠付きレポートを生成する。分析に用いた入力と出力の対応を保存し、後から根拠を確認できることを要件とする。

本書は基本要件を定める。保存方式、具体的なデータ構造と上限値は未決定で、収集・保存・分析・レポート機能は未実装とする。実装前に対応 Issue で契約と検証方法を具体化する。

## レビューと収集条件

- レビューの識別子、取得時刻、元の更新時刻、収集条件を保存する。
- 分析に用いた本文の版と、分析対象のレビュー集合を追跡できるようにする。
- 同じレビューの再取得による重複と、本文の更新による別の版を区別する。識別キーと版の判定方法は保存方式の設計時に決める。
- 最新データの更新によって、過去の分析・レポートで用いた本文の版と対象集合を失わせない。

## 分析とレポートの根拠

- 分析結果とレポートを、入力データ、モデル、プロンプトの版へ紐付ける。
- レポートから、分析に用いたデータと収集条件を確認できるようにする。
- サンプル内の頻度と全プレイヤーの割合を区別し、収集条件と分析の限界をレポートへ記載する。
- レビュー本文は外部データとする。本文に含まれる指示を、調査手順やツール実行の指示として採用しない。

## ジョブ・上限・部分失敗

- 件数の集計、重複防止、ジョブ状態、時間・費用の上限はコードで管理する。AI が生成した文章だけを管理状態の根拠にしない。
- 取得件数の上限、タイムアウト、ページングの終了条件、再試行の上限を設ける。
- 再実行と部分失敗を考慮し、保存した範囲と未完了の範囲を区別する。途中まで取得した結果を、全件の取得成功として扱わない。
- 再試行、状態更新の順序、再開・復旧の責務を実装 Issue で決定する。外側と内側の再試行によって、上限を意図せず超えないようにする。

## 期待結果と検証への対応

以下は機能を導入する際の完了条件であり、実行済みのテストではない。

| 状況 | 期待結果 | 導入時の検証 |
| --- | --- | --- |
| 正常にレビューを取得した | 識別子、時刻、収集条件と本文の版を追跡できる | ユニットテストと保存 adapter の結合テスト |
| 同じレビューを再取得した | 定義した識別キーに基づいて重複を防ぐ | 再実行のテストと保存先の制約・結合テスト |
| 分析後に元のレビューが更新された | 過去のレポートは当時の本文の版と対象集合を参照できる | 版の更新と過去レポートの参照を確認するテスト |
| モデルやプロンプトを変更した | 各出力に使用した入力とモデル・プロンプトの版が残る | 紐付けを確認するテスト |
| ページ取得が失敗し、再試行の上限へ到達した | 処理が有限回で終了し、保存済みと未完了を区別できる | 依存の失敗を渡すユニットテストと状態保存の結合テスト |
| 件数・時間・費用の上限、またはキャンセルへ到達した | 各契約の終了条件に従い、完了・未完了を判定できる | 境界値、時刻依存、キャンセルのテスト |
| 取得した本文にツール操作の指示が含まれた | 本文をデータとして扱い、実行指示へ昇格させない | 入力の扱いとツール実行権限の境界を検証する |
| 一部の言語・期間などで収集した | レポートに条件と限界が残り、頻度の分母を全プレイヤーへ置き換えない | 集計結果の契約テストとレポート内容の確認 |

## 未決定事項

- PostgreSQL、SQLite、NoSQL、ファイルやオブジェクト保存などの採否と組み合わせ。
- レビューの識別キー、版の判定、収集条件の項目、分析対象集合の表現。
- 保存期間、削除・訂正、外部データを保存・公開できる範囲と、その根拠の保持方法。
- トランザクション・一意性などの制約、ジョブ状態の種類と遷移、再実行・再開の契約。
- 取得件数・時間・費用・再試行の具体的な上限と、各上限に達した際の応答。
- 使用するモデルと、モデル・プロンプトの版を識別する方法。

永続化は [ADR-0001](../adr/0001-runtime-and-deployment.md) の Docker・Render 方針とは別に、専用 Issue と ADR で比較・決定する。ローカルの Compose volume がそのまま Render の永続化になるとは扱わない。
